# 第 7 章 选型决策手册

> 面对一个新任务——先 RAG，再 LoRA，最后才考虑全量微调

## 决策的两个核心维度

工程实践中最常见的问题：**"我有这些数据和这台机器，用什么方法？"** 答案由两个维度决定：**数据量**和**硬件**。

在此之前，先问一个更根本的问题：**目标是"让模型知道更多知识"还是"改变模型的输出行为"？**

- 知识扩充（特定文档库问答）→ **优先考虑 RAG**，成本低、可实时更新
- 行为/风格/格式调整（特定任务格式、输出风格）→ 考虑微调

RAG 几乎总是比微调更快更便宜地解决知识问题。两者也可以组合：先 RAG 检索上下文，再用微调好的模型生成高质量回答。

## 数据量决策表

| 数据规模 | 场景 | 推荐方法 | 理由 |
|---------|------|---------|------|
| **< 200 条** | 极少数据，验证 POC | Prompt Engineering / RAG | 数据不够训练，先试 prompt |
| **200–2k 条** | 小规模定制 | LoRA（r=8, 1-2 epoch） | 低秩适应足够，过拟合风险低 |
| **2k–20k 条** | 典型微调场景 | LoRA（r=16–32）/ QLoRA | 标准做法，可以加 DPO 对齐 |
| **20k–200k 条** | 垂直领域全量微调 | Full SFT + LoRA 混合 | 数据充足，可考虑更高 rank |
| **> 200k 条** | 从头 SFT 大模型 | Full fine-tuning | 接近预训练规模，LoRA 可能欠拟合 |

## 硬件×方法矩阵

| 硬件 | 显存 | 可以做什么 |
|------|------|-----------|
| Mac M2/M3 | 16–48 GB 统一内存 | QLoRA（MLX）7B 模型；GGUF 推理 70B |
| RTX 3090/4090 | 24 GB | QLoRA 7B–13B；LoRA 7B fp16 |
| A100 40GB | 40 GB | Full SFT 7B；LoRA 13B fp16 |
| A100 80GB | 80 GB | Full SFT 13B；LoRA 70B；DPO 13B |
| 8× A100 | 640 GB | Full SFT 70B；PPO 13B |

## 方法对比矩阵

| 方法 | 显存（7B） | 训练速度 | 最终质量 | 适用场景 |
|------|-----------|---------|---------|---------|
| Full SFT fp16 | 80 GB | 最快 | 最高 | 数据充足 + 多 GPU |
| LoRA r=16 fp16 | 18 GB | 快 | 高（差 1–2%）| 单卡 A100 |
| QLoRA NF4 r=16 | 11 GB | 中 | 中高（差 2–4%）| 单卡 3090 |
| DPO（LoRA 基础上）| 18 GB | 中 | 对齐最佳 | 有偏好数据 |
| PTQ INT4 GPTQ | 5 GB（推理）| 推理最快 | 接近 fp16 | 部署优先 |

## 完整决策流程

```
有任务需求
    │
    ▼
目标是扩充知识？
├── 是 → RAG（向量库 + 检索）→ 足够则止步
└── 否（改变行为/格式）
        │
        ▼
    数据量 < 200 条？
    ├── 是 → Prompt engineering
    └── 否
            │
            ▼
        硬件 ≤ 24GB（单卡 3090/4090 或 Mac）？
        ├── 是 → QLoRA（MLX / bitsandbytes）
        └── 否（A100 40GB+）
                │
                ▼
            数据量 > 20k 且需要最高质量？
            ├── 是 → Full SFT
            └── 否 → LoRA r=16–32
                        │
                        ▼
                    有偏好数据且需要对齐？
                    ├── 是 → 在 LoRA/SFT 基础上加 DPO
                    └── 否 → 部署 → PTQ 量化推理
```

## 常见误区与经验法则

::: warning 三个常见误区
1. **用算法解决数据问题**：数据质量差时，再好的微调方法也救不了。先清洗数据。
2. **一上来就全量微调**：LoRA r=16 通常能达到全量微调 95%+ 的效果，代价却低 5-10 倍。
3. **过度训练**：epoch=10 不如 epoch=2。SFT 一般 1-3 个 epoch 足够，过多会灾难性遗忘。
:::

::: tip 经验法则总结
- **先 RAG，再 LoRA，最后才考虑全量微调**
- **LoRA r=16 是最通用的起点**：在大多数对话任务上效果与 r=64 相差不超过 1-2%，但快 4 倍
- **DPO 是廉价的对齐升级**：在 SFT 基础上加 DPO 通常只需多 1-2 GPU×小时，但对齐质量显著提升
- **量化是免费的午餐**：Q4_K_M GGUF 相对 fp16 质量损失 < 3%，但显存节省 4×，推理速度提升 2×
:::

## 与生产对应

决策过程参考 `peft` 官方文档的 Performance Guide；多卡训练用 `accelerate` + `deepspeed`（ZeRO-3 可把 70B 模型的显存分摊到多卡）；自动选型工具 `optimum`；生产推理框架 `vLLM`（支持 GPTQ/AWQ 量化 + 连续批处理，吞吐量是 transformers 的 10-20 倍）。
