## 1. 为什么 LLM 应用需要缓存

### 1.1 LLM 调用的三大痛点

```
痛点一：成本高
  GPT-4o: 输入 $2.50/1M tokens, 输出 $10.00/1M tokens
  一个日活 10 万的客服机器人，一天可能花费数百美元

痛点二：延迟高
  LLM 推理通常需要 1-5 秒
  用户体验：每次提问都要等好几秒

痛点三：重复调用浪费
  客服场景：70% 的问题是重复的（退货政策、营业时间等）
  这些重复调用完全是浪费！
```

### 1.2 缓存的价值量化

```
场景：客服机器人，日均 1000 请求，70% 重复率

  无缓存：1000 次 API 调用 = ¥10.00/天
  有缓存：300 次 API 调用 = ¥3.00/天

  节省：70% 成本 + 99% 延迟（缓存命中时 <1ms vs API 2s）

对应 cache_demo.py Chapter 0 的成本演算部分
```

```
          ┌─────────────┐
          │ API 层缓存   │ ← Anthropic Prompt Caching
```

## 3. 精确匹配缓存（Exact Match Cache）

### 3.1 工作原理

```
精确匹配 = 问题文字完全一样才命中

  cache_key = hash(model + prompt + parameters)

  "什么是缓存？" → hash → key_abc123 → 查找 → 命中/未命中
  "缓存是什么？" → hash → key_def456 → 查找 → 未命中!（文字不同）

  ┌─────────────────────────────────────────────────────┐
  │  Cache Store (dict / SQLite / Redis)                 │
  │                                                     │
  │  key_abc123  →  "缓存是计算机中用于..."              │
  │  key_def456  →  "数据库是一种..."                    │
  │  key_ghi789  →  "Python是一种..."                   │
  └─────────────────────────────────────────────────────┘
```

### 3.2 优缺点

```
优点：
  - 实现简单（就是一个 dict/hash table）
  - 查询极快（O(1) 时间复杂度）
  - 100% 准确（不会返回错误答案）

缺点：
  - 命中率低（"什么是缓存" vs "缓存是什么" 被视为不同问题）
  - 对用户输入敏感（多一个空格就不命中）

对应 cache_demo.py Chapter 1 (InMemoryCache) 和 Chapter 2 (SQLiteCache)
```

## 4. 语义缓存（Semantic Cache）

### 4.1 核心思想

```
语义缓存 = 意思相近就命中（而非文字相同）

  工作流程：
  ┌────────────┐    ┌──────────────┐    ┌──────────────┐
  │ 用户问题    │ →  │ Embedding    │ →  │ 向量搜索     │
  │ "天气如何"  │    │ [0.12,0.87..] │    │ (FAISS)      │
  └────────────┘    └──────────────┘    └──────────────┘
                                              │
                                    相似度 > 阈值?
                                        │        │
                                      Yes        No
                                        ↓        ↓
                                    返回缓存   调用LLM

  数学基础：余弦相似度
    cos_sim(A, B) = (A · B) / (|A| × |B|)

    向量已归一化时：cos_sim = 点积（Inner Product）
    阈值通常设为 0.85~0.95
```

### 4.2 实现细节

```python
# 对应 cache_demo.py 的 SemanticCache 类

class SemanticCache:
    def __init__(self, embedding_model, threshold=0.85):
        self.index = faiss.IndexFlatIP(dimension)  # FAISS 向量索引
        self.answers = []                           # 对应答案列表
        self.threshold = threshold                  # 相似度阈值

    def get(self, question):
        vec = embedding_model.embed_query(question)
        distances, indices = self.index.search(vec, 1)
        if distances[0][0] >= self.threshold:
            return self.answers[indices[0][0]]  # 命中!
        return None  # 未命中
```

### 4.3 阈值选择

```
阈值太高（如 0.98）：几乎不命中，等于没有缓存
阈值太低（如 0.70）：容易误命中，返回不相关的答案

  相似度      判断        风险
  ─────────────────────────────
  > 0.95      几乎相同    极低风险
  0.85~0.95   语义相近    低风险（推荐）
  0.75~0.85   有些关联    中风险
  < 0.75      不太相关    高风险

生产建议：从 0.90 开始，根据误命中率逐步调低
```

## 5. LLM 缓存实现（LangChain 内置）

### 5.1 InMemoryCache

```python
# 对应 cache_demo.py Chapter 1

from langchain_core.globals import set_llm_cache
from langchain_core.caches import InMemoryCache

set_llm_cache(InMemoryCache())  # 全局设置

# 之后所有 LangChain LLM 调用自动走缓存
response = llm.invoke("什么是缓存？")  # 第一次: API 调用
response = llm.invoke("什么是缓存？")  # 第二次: 缓存命中(< 1ms)
```

### 5.2 SQLiteCache

```python
# 对应 cache_demo.py Chapter 2

from langchain_community.cache import SQLiteCache

set_llm_cache(SQLiteCache(database_path=".cache.db"))

# 数据库表结构:
# ┌─────────┬──────────┬────────────┐
# │ prompt  │ llm_str  │ response   │
# ├─────────┼──────────┼────────────┤
# │ "..."   │ "gpt-4"  │ "答案..."  │
# └─────────┴──────────┴────────────┘
#
# 优势: 程序重启后缓存仍在
```

### 5.3 Redis Cache（生产首选）

```python
from langchain_community.cache import RedisCache
import redis

redis_client = redis.Redis(host="localhost", port=6379)
set_llm_cache(RedisCache(redis_client))

# Redis 优势:
# - 分布式: 多个服务实例共享缓存
# - 原生 TTL: 自动过期
# - 高性能: 毫秒级读写
# - 持久化: RDB/AOF 防数据丢失
```

## 6. 分布式缓存（Redis）

### 6.1 架构设计

```
  ┌────────────┐  ┌────────────┐  ┌────────────┐
  │ App Node 1 │  │ App Node 2 │  │ App Node 3 │
  └─────┬──────┘  └─────┬──────┘  └─────┬──────┘
        │                │                │
        └────────────────┼────────────────┘
                         ↓
              ┌─────────────────────┐
              │    Redis Cluster     │
              │  (Sentinel 主从)     │
              │                     │
              │  key → value + TTL  │
              └─────────────────────┘

  任何节点写入的缓存，其他节点都能读到
  → 集群级别的缓存共享
```

### 6.2 Redis 缓存键设计

```
推荐 key 格式:
  llm_cache:{model}:{hash(prompt+params)}

示例:
  llm_cache:gpt-4o:sha256_abc123def456

Redis 命令:
  SET llm_cache:gpt-4o:abc123 "答案..." EX 3600  # 1小时过期
  GET llm_cache:gpt-4o:abc123
```

## 7. 缓存键设计

### 7.1 影响缓存键的因素

```
缓存键必须包含所有影响输出的变量:

  cache_key = hash(
      model_name,       # 不同模型输出不同
      system_prompt,    # 不同 prompt 输出不同
      user_message,     # 核心: 用户问题
      temperature,      # temperature=0 才适合缓存
      top_p,            # 采样参数
      max_tokens,       # 可能影响输出完整性
  )

  注意: 以下变量通常不放入 key:
    - timestamp (时间戳变化导致永不命中)
    - request_id (唯一性标识)
    - user_id (除非需要个性化缓存)
```

### 7.2 Temperature 与缓存的关系

```
temperature = 0:
  同一输入总是得到相同输出 → 缓存效果最佳

temperature > 0:
  同一输入每次输出不同 → 缓存返回固定答案
  → 可能不符合预期（用户期望多样性）

结论:
  ┌──────────────────────────────────────────┐
  │ 适合缓存: temperature=0 的场景           │
  │   - 信息提取、分类、问答                  │
  │   - 固定格式输出                          │
  │                                          │
  │ 不适合缓存: temperature>0 的场景          │
  │   - 创意写作、头脑风暴                    │
  │   - 需要多样性的对话                      │
  └──────────────────────────────────────────┘

对应 cache_demo.py 中 llm 设置 temperature=0
```

## 8. 缓存失效策略

### 8.1 TTL（Time To Live）— 按时间过期

```
原理: 缓存条目在指定时间后自动删除

  cache.set(key, value, ttl=3600)  # 1 小时后过期

适用场景:
  - 天气查询 (TTL=30分钟)
  - 新闻摘要 (TTL=1小时)
  - 产品价格 (TTL=24小时)
  - 公司政策 (TTL=7天)

Redis 原生支持:
  SET key value EX 3600
  TTL key  → 查看剩余生存时间
```

### 8.2 LRU（Least Recently Used）— 最近最少使用

```
原理: 缓存满时，淘汰最久没被访问的条目

  容量上限: 1000 条
  ┌───────────────────────────────────────┐
  │ 最近访问 ←─────────────────→ 最久未用 │
  │  [条目A] [条目C] [条目B] ... [条目Z]  │
  │                                       │
  │  新条目进来 → 如果已满 → 删除条目Z    │
  │  条目B被访问 → 移到最前面             │
  └───────────────────────────────────────┘

Python 实现: collections.OrderedDict 或 functools.lru_cache
Redis 实现: 配置 maxmemory-policy allkeys-lru
```

### 8.3 LFU（Least Frequently Used）— 最不经常使用

```
原理: 缓存满时，淘汰访问次数最少的条目

  条目A: 访问 100 次 → 保留
  条目B: 访问 2 次   → 淘汰候选
  条目C: 访问 50 次  → 保留

优势: 比 LRU 更合理（高频问题永远保留）
劣势: 新条目初始频率低，可能被过早淘汰

Redis 实现: maxmemory-policy allkeys-lfu
```

### 8.4 版本控制失效

```
key = f"{model_version}:{prompt_version}:{hash(input)}"

模型升级时:
  旧 key: v1:p1:abc123 → 自然失效（不再查询）
  新 key: v2:p1:abc123 → 新缓存

Prompt 更新时:
  旧 key: v2:p1:abc123 → 自然失效
  新 key: v2:p2:abc123 → 新缓存

对应 cache_demo.py Step 4.2 的版本控制说明
```

## 9. 缓存命中率优化

### 9.1 输入标准化

```
问题: 用户输入千变万化
  "什么是缓存？"
  " 什么是缓存？"    ← 多了空格
  "什么是缓存"       ← 少了问号
  "请问什么是缓存？"  ← 多了"请问"

解决: 在查缓存前标准化输入
  normalize(input):
    1. strip()           → 去首尾空格
    2. 去标点            → 统一处理
    3. 小写化(英文)      → "What" = "what"
    4. 同义词替换(可选)  → "如何" = "怎样"
```

### 9.2 分层缓存策略

```
┌──────────────────────────────────────────────────┐
│  L1: InMemoryCache (进程内, <0.1ms)              │
│    ↓ 未命中                                      │
│  L2: Redis Cache (网络, ~1ms)                    │
│    ↓ 未命中                                      │
│  L3: Semantic Cache (向量计算, ~10ms)            │
│    ↓ 未命中                                      │
│  L4: LLM API 调用 (网络+推理, ~2000ms)           │
└──────────────────────────────────────────────────┘

命中率 = L1命中 + L2命中 + L3命中
       = 精确匹配热点 + 精确匹配长尾 + 语义相近
```

### 9.3 命中率监控

```
关键指标:
  hit_rate = cache_hits / total_requests × 100%

  理想值:
    精确缓存: 30-50% (客服场景可达 70%)
    语义缓存: 50-80%

  告警阈值:
    hit_rate < 20% → 检查缓存配置
    hit_rate 突降  → 可能有大量新问题涌入或缓存失效
```

## 10. Prompt Caching（API 层面缓存）

### 10.1 什么是 Prompt Caching

```
传统缓存: 缓存完整的 (输入, 输出) 对
Prompt Caching: 缓存输入中的重复前缀部分

  场景: 你有一个 3000 token 的 System Prompt，每次调用都发送

  ┌────────────────────────────────────────────────────┐
  │  请求1: [System Prompt 3000t] + [用户问题A 50t]    │
  │  请求2: [System Prompt 3000t] + [用户问题B 30t]    │
  │  请求3: [System Prompt 3000t] + [用户问题C 80t]    │
  │                                                    │
  │  前缀相同!  ──→ 只计算一次，后续复用               │
  └────────────────────────────────────────────────────┘
```

### 10.2 Anthropic Prompt Caching

```
Anthropic 的实现:
  - 缓存 System Prompt / 长上下文前缀
  - 缓存命中时，前缀 token 价格降低 90%
  - 缓存有效期: 5 分钟（自动刷新）

API 用法:
  messages = [
      {"role": "system", "content": [
          {"type": "text", "text": long_prompt, "cache_control": {"type": "ephemeral"}}
      ]},
      {"role": "user", "content": "用户问题"}
  ]

计费:
  普通输入:     $3.00 / 1M tokens
  缓存写入:     $3.75 / 1M tokens (首次，多 25%)
  缓存命中:     $0.30 / 1M tokens (后续，省 90%)
```

### 10.3 OpenAI 类似功能

```
OpenAI Cached Tokens (2024+):
  - 自动检测重复前缀
  - 缓存命中时输入价格减半
  - 无需手动标记，自动生效
  - 在 response.usage 中体现 cached_tokens 字段
```

## 11. 成本节省分析

### 11.1 计算公式

```
对应 cache_demo.py Step 4.3

月度节省 = 日请求量 × 命中率 × 单次成本 × 30

示例计算:
  日请求: 10,000
  命中率: 65%
  平均 token/次: 600 (输入100 + 输出500)
  价格: $0.002 / 1K tokens

  无缓存月成本: 10000 × 600/1000 × $0.002 × 30 = $360
  有缓存月成本: 10000 × 0.35 × 600/1000 × $0.002 × 30 = $126
  月度节省: $234 (65%)
```

### 11.2 缓存本身的成本

```
缓存不是免费的，需要考虑:

  存储成本:
    - Redis: 约 $0.1/GB/月 (云服务)
    - 1 万条缓存 × 平均 1KB/条 = 10MB → 几乎为零

  计算成本 (语义缓存):
    - Embedding 计算: 约 $0.0001/次
    - FAISS 向量搜索: CPU 时间可忽略

  ROI 通常极高:
    缓存成本 << 节省的 LLM API 成本
```

## 12. 缓存一致性问题

### 12.1 常见一致性问题

```
问题1: 知识库更新后缓存过期
  知识库: "营业时间 9:00-18:00" → 更新为 "9:00-21:00"
  缓存: 仍然返回旧答案 "营业时间是9点到18点"
  → 用户得到错误信息!

问题2: 模型升级后缓存不一致
  旧模型: 回答质量一般
  新模型: 回答质量更好
  缓存: 仍然返回旧模型的回答
  → 用户体验不一致!

问题3: 多节点缓存不同步
  节点A: 已更新缓存
  节点B: 仍用旧缓存
  → 同一用户可能得到不同答案!
```

### 12.2 解决方案

```
方案一: 事件驱动失效
  知识库更新 → 发布事件 → 清除相关缓存
  实现: Redis Pub/Sub 或消息队列

方案二: 版本化 key
  key 中包含数据版本号
  数据更新 → 版本号+1 → 旧缓存自然失效

方案三: 合理 TTL
  根据数据变化频率设置 TTL
  高频变化(价格): TTL=5分钟
  低频变化(政策): TTL=24小时

方案四: 写穿透(Write-Through)
  更新数据时同时更新缓存
  保证缓存与数据源始终一致
```

## 13. 缓存预热策略

### 13.1 什么是缓存预热

```
问题: 系统刚启动时缓存为空，所有请求都是 Cache Miss
     → 启动初期延迟高、成本高（"冷启动"问题）

解决: 在系统启动前/启动时，主动填充热点数据到缓存

  ┌──────────────────────────────────────────────┐
  │  系统启动                                     │
  │    ↓                                         │
  │  加载 Top 100 高频问题                        │
  │    ↓                                         │
  │  批量调用 LLM 生成答案                        │
  │    ↓                                         │
  │  写入缓存                                     │
  │    ↓                                         │
  │  开始接受请求 (缓存已有数据，命中率立刻很高)  │
  └──────────────────────────────────────────────┘
```

### 13.2 预热数据来源

```
1. 历史日志分析
   统计过去 30 天最高频的问题 → 预热

2. 业务知识库
   把 FAQ 列表全部预热到缓存

3. 定时预热
   每天凌晨重新生成热点缓存（保证答案新鲜度）

4. 渐进式预热
   系统启动后，逐步扩大缓存（避免启动时大量 API 调用）
```

```
  ┌─────────────────────────────────────────────────────────────┐
```

### 14.2 生产最佳实践清单

```
1. 缓存策略
   □ temperature=0 用于需要缓存的场景
   □ 缓存 key 包含所有影响输出的参数
   □ 合理设置 TTL（根据数据时效性）
   □ 实现分层缓存 (L1 内存 + L2 Redis)

2. 监控与告警
   □ 监控缓存命中率 (目标 > 50%)
   □ 监控缓存延迟 (Redis < 5ms)
   □ 监控缓存容量 (避免 OOM)
   □ 命中率突降告警

3. 数据一致性
   □ 知识库更新时清除相关缓存
   □ 模型升级时版本化 key
   □ 设置合理的 TTL 兜底

4. 安全与隔离
   □ 多租户场景缓存隔离 (key 含 tenant_id)
   □ 敏感信息不缓存 (或加密存储)
   □ 缓存容量限制 (防止内存泄漏)

5. 不适合缓存的场景 (对应 cache_demo.py Step 4.4)
   □ 创意生成 (每次应不同)
   □ 实时数据查询 (股价、天气)
   □ 强个性化回答 (需含 user_id)
   □ 多轮对话上下文相关的回复
```
