## 1. 为什么需要评估

### 1.1 从直觉开发到科学开发

```
对应 rag_eval.py 前置科普一：

没有评估的开发（盲人摸象）：
  ┌─────────────────────────────────────────────────────────────┐
  │  改了 chunk_size → "试了几个问题，感觉还行" → 上线         │
  │  换了 Embedding  → "好像回答更准了？"       → 上线         │
  │  调了 Prompt     → "看起来没变差"           → 上线         │
  │                                                             │
  │  结果：上线后用户投诉"回答不准"，但不知道哪里退步了！      │
  └─────────────────────────────────────────────────────────────┘

有评估的开发（科学实验）：
  ┌─────────────────────────────────────────────────────────────┐
  │  准备评估集（50个标准问答对）                                │
  │  改了 chunk_size → 跑评估 → 忠实度 82%→85% ✅ 上线         │
  │  换了 Embedding  → 跑评估 → 相关性 78%→72% ❌ 回滚         │
  │  调了 Prompt     → 跑评估 → 整体 +3%       ✅ 上线         │
  │                                                             │
  │  每次改动都有数字说话，退步立刻能发现！                     │
  └─────────────────────────────────────────────────────────────┘
```

### 1.2 评估的三大价值

```
① 质量保障：确保上线前达到最低质量标准
② 回归检测：发现改动带来的负面影响
③ 优化指导：知道"哪里不好"才能有针对性改进

类比：
  不做评估 = 不考试就发毕业证
  做评估   = 每次改进都要通过考试验证
```

## 2. LLM 评估的挑战

### 2.1 为什么 LLM 评估特别难

```
传统软件测试：
  输入 → 确定性输出 → assert(output == expected)  简单！

LLM 评估：
  输入 → 概率性输出 → ???  如何判断"好坏"？

核心困难：
  ┌──────────────────────────────────────────────────────────────┐
  │ 困难                    │ 说明                               │
  ├──────────────────────────────────────────────────────────────┤
  │ 输出非确定性            │ 同一问题每次回答不同               │
  │ "正确"的定义模糊        │ "约28亿"和"28.3亿"都算对吗？      │
  │ 多维度质量              │ 准确+流畅+完整+安全，如何综合？    │
  │ 主观性                  │ 不同人对"好回答"的标准不同         │
  │ 缺乏 ground truth      │ 开放式问题没有标准答案             │
  │ 评估本身也不完美        │ 评估器也可能犯错                   │
  └──────────────────────────────────────────────────────────────┘
```

### 2.2 评估层次

```
从易到难的评估层次：

  Level 1: 格式正确性（JSON是否valid、字段是否完整）
     → 确定性检查，最简单

  Level 2: 事实正确性（数字是否准确、实体是否正确）
     → 可对比 ground truth

  Level 3: 语义质量（是否忠实、是否完整、是否连贯）
     → 需要 LLM-as-Judge 或人工评估

  Level 4: 用户满意度（用户是否觉得有用）
     → 最难量化，需要线上指标
```

## 3. 自动评估指标

### 3.1 BLEU（Bilingual Evaluation Understudy）

```
原理：计算生成文本与参考文本的 n-gram 重合度

公式：
  BLEU = BP × exp(Σ w_n × log(p_n))

  其中：
    p_n = 匹配的n-gram数 / 生成文本的n-gram总数
    BP  = min(1, exp(1 - ref_len/gen_len))  (长度惩罚)
    w_n = 1/N (通常 N=4，即考虑1-4gram)

示例：
  参考: "今天天气很好"
  生成: "今天天气不错"

  1-gram匹配: 今天(✓) 天气(✓) 很(✗) 好(✗) → p1 = 2/4 = 0.5
  2-gram匹配: 今天天气(✓) 天气很(✗) 很好(✗) → p2 = 1/3 = 0.33

局限性：
  - 只看字面重合，不理解语义
  - "28.3亿" vs "约28亿" → BLEU很低，但语义等价
  - 适合翻译任务，不太适合开放式生成
```

### 3.2 ROUGE（Recall-Oriented Understudy for Gisting Evaluation）

```
原理：侧重召回率（参考文本中有多少内容出现在生成文本中）

三种变体：
  ROUGE-1: 1-gram 召回率
  ROUGE-2: 2-gram 召回率
  ROUGE-L: 最长公共子序列 (LCS) 比率

公式（ROUGE-N）：
  Recall = 匹配n-gram数 / 参考文本n-gram总数
  Precision = 匹配n-gram数 / 生成文本n-gram总数
  F1 = 2 × P × R / (P + R)

适用场景：摘要评估（生成的摘要覆盖了多少原文要点）
```

### 3.3 BERTScore

```
原理：用 BERT 嵌入计算语义相似度（而非字面匹配）

流程：
  1. 将参考文本和生成文本的每个 token 用 BERT 编码为向量
  2. 计算每对 token 之间的余弦相似度
  3. 用贪心匹配找最优对齐
  4. 计算 Precision, Recall, F1

优势：
  "28.3亿" vs "约28亿" → BERTScore 高（语义相近）
  "好的天气" vs "不错的天气" → BERTScore 高

局限：
  - 需要 BERT 模型推理，速度较慢
  - 对事实性错误不够敏感（"28亿"vs"50亿"可能相似度也不低）
```

### 3.4 METEOR

```
原理：在 BLEU 基础上增加同义词匹配和词干匹配

改进点：
  ① 同义词匹配：happy ↔ glad 也算匹配
  ② 词干匹配：running ↔ run 也算匹配
  ③ 碎片惩罚：匹配片段越连续越好

比 BLEU 更好地处理措辞变化，但仍是词级别匹配
```

### 3.5 传统指标的局限

```
所有传统指标的共同问题：

  参考: "公司今年营收28.3亿，同比增长87%"

  回答A: "公司今年营收28.3亿元，同比增长87%"
    → BLEU: 0.95 (高) ← 几乎一样，正确！

  回答B: "公司今年营收50亿，同比增长200%"
    → BLEU: 0.60 (中) ← 格式相似但数字全错！

  回答C: "智驾科技2024年实现营业收入约28亿，较上年增长近9成"
    → BLEU: 0.15 (低) ← 措辞完全不同但内容正确！

结论：传统指标无法胜任 LLM 输出评估
     → 需要 LLM-as-Judge
```

## 4. RAG 专用指标

### 4.1 三大核心指标

对应 `rag_eval.py` 前置科普二：

```
┌─────────────────────────────────────────────────────────────┐
│  指标一：检索相关性（Context Relevance）                      │
│  问题：检索到的文档和用户问题相关吗？                        │
│                                                             │
│  问: "2024年营收？" → 检索到财务数据 → 相关 ✅             │
│  问: "2024年营收？" → 检索到员工手册 → 不相关 ❌           │
├─────────────────────────────────────────────────────────────┤
│  指标二：忠实度（Faithfulness / Groundedness）               │
│  问题：回答是否基于检索到的文档？有没有编造？               │
│                                                             │
│  文档说"28亿"，回答说"28亿" → 忠实 ✅                     │
│  文档说"28亿"，回答说"50亿" → 幻觉 ❌                     │
├─────────────────────────────────────────────────────────────┤
│  指标三：答案正确性（Answer Correctness）                     │
│  问题：最终答案和标准答案一致吗？                            │
│                                                             │
│  标准答案"28.3亿"，回答"约28亿" → 正确 ✅                 │
│  标准答案"28.3亿"，回答"15亿"   → 错误 ❌                 │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 指标之间的关系

```
三个指标的因果链：

  检索相关性 → 影响 → 忠实度 → 影响 → 答案正确性

  检索到错误的文档 → LLM 基于错误文档回答 → 答案必然错误

  但反过来不一定：
    检索正确 + LLM 幻觉 → 忠实度低 → 答案可能错误
    检索正确 + LLM 忠实 + 信息不完整 → 答案可能不完整

诊断指南：
  正确性低，忠实度高 → 检索问题（检索到了但信息不够）
  正确性低，忠实度低 → 幻觉问题（LLM 在编造）
  忠实度低，相关性高 → LLM Prompt 问题（有文档但不用）
  忠实度低，相关性低 → 检索问题（检索到无关内容）
```

### 4.3 扩展指标

```
RAGAS 框架定义的更多指标：

  Context Precision:  检索结果中相关文档排在前面的比例
  Context Recall:     ground truth 中的信息被检索到的比例
  Answer Relevance:   回答是否切题（不是正确但离题）
  Answer Similarity:  回答与标准答案的语义相似度

信息检索经典指标：
  MRR (Mean Reciprocal Rank):  第一个正确结果的排名倒数
  nDCG (Normalized DCG):       考虑排序的相关性评分
  Hit Rate:                    top-K中是否包含正确文档
```

## 5. LLM-as-Judge 评估范式

### 5.1 核心原理

```
对应 rag_eval.py 前置科普三：

传统方法（BLEU/ROUGE）→ 只看字面重合 → 不理解语义
LLM-as-Judge → 让 LLM 当"阅卷老师" → 理解语义

流程：
  ① 给 LLM 评分标准（rubric）
  ② 给 LLM 参考答案 + 待评回答
  ③ LLM 打分（如1-5分）+ 给出理由

为什么有效：
  LLM 能理解"28.3亿"和"约28亿"是同一个意思
  LLM 能判断论述的逻辑是否连贯
  LLM 能识别幻觉和编造
```

### 5.2 评估 Prompt 设计

对应 `rag_eval.py` 中的三个评估 Prompt：

```
关键设计要素：

  ① 明确角色："你是一位严格的XX评估专家"
  ② 评分标准 (Rubric)：每个分数对应什么质量
     5分: 完全正确，包含所有关键信息
     4分: 基本正确，覆盖大部分关键信息
     3分: 部分正确，有遗漏但无明显错误
     2分: 有错误信息
     1分: 完全错误或答非所问
  ③ 注意事项："表述不同但含义相同应视为正确"
  ④ 输出格式：结构化输出（score + reasoning）
```

### 5.3 结构化输出保证解析

对应代码中的 Pydantic 模型：

```python
class EvalScore(BaseModel):
    score: int = Field(description="评分，1-5分")
    reasoning: str = Field(description="评分理由")

# 使用 with_structured_output 保证返回可解析的结构
eval_structured = eval_llm.with_structured_output(EvalScore)
```

### 5.4 LLM-as-Judge 的偏见

```
已知偏见：
  ① 位置偏见：先看到的选项更容易得高分
  ② 冗长偏见：更长的回答往往得分更高
  ③ 自我偏见：评估自己模型的输出时打分偏高
  ④ 风格偏见：喜欢特定的表达风格

缓解方法：
  - 多评委共识（用多个LLM评分取平均）
  - 随机化顺序（A/B评估时随机交换位置）
  - 人工校准（定期用人工评估校准LLM偏差）
  - 用更强的模型当评委（GPT-4评估GPT-3.5）
```

## 6. 人工评估方法

### 6.1 评估方式

```
┌──────────────────────────────────────────────────────────────┐
│ 方式               │ 说明                  │ 适用场景        │
├──────────────────────────────────────────────────────────────┤
│ 绝对评分           │ 对单个回答打1-5分     │ 质量基准测量    │
│ 相对排序           │ 对比两个回答选更好的  │ A/B测试        │
│ 标注细粒度错误     │ 标出哪里错/哪里好     │ 诊断问题原因    │
│ 偏好投票           │ 多人投票选最佳        │ 众包评估        │
└──────────────────────────────────────────────────────────────┘
```

### 6.2 标注员一致性

```
度量标注员之间的一致性：

  Cohen's Kappa:
    κ = (P_o - P_e) / (1 - P_e)
    P_o = 实际一致率
    P_e = 随机一致率

    κ > 0.8: 几乎完全一致（优秀）
    κ 0.6-0.8: 基本一致（可接受）
    κ < 0.6: 一致性不够（需要改进标注规范）

提高一致性的方法：
  - 详细的标注指南 + 示例
  - 标注前培训
  - 争议样本讨论达成共识
```

## 7. 评估数据集构建

### 7.1 数据集构成

对应 `rag_eval.py` 中的 `EVAL_DATASET`：

```
每条评估数据包含：
  question:       测试问题
  ground_truth:   人工标注的标准答案
  eval_type:      问题类型（事实型/对比型/推理型）
  contexts:       理想检索结果（可选）

示例：
  {
    "question": "智驾科技2024年的总营收是多少？",
    "ground_truth": "28.3亿元人民币",
    "eval_type": "事实提取",
  }
```

### 7.2 构建原则

```
评估集质量决定评估价值！

  ┌─────────────────────────────────────────────────────────────┐
  │ 原则               │ 说明                                   │
  ├─────────────────────────────────────────────────────────────┤
  │ ① 覆盖度          │ 覆盖多种问题类型（事实/对比/推理/规划）│
  │ ② 精确性          │ 标准答案数字、名称必须准确             │
  │ ③ 充分数量        │ 至少 30-50 条，覆盖核心业务场景        │
  │ ④ 定期更新        │ 知识库变了，评估集也要跟着变           │
  │ ⑤ 难度梯度        │ 包含简单/中等/困难问题                 │
  │ ⑥ 边界情况        │ 包含"无法回答"的问题                   │
  └─────────────────────────────────────────────────────────────┘
```

### 7.3 自动生成评估集

```
方法：用 LLM 基于知识库自动生成问答对

  文档块 → LLM → 生成 (问题, 答案) 对
                → 人工审核和修正
                → 正式评估集

Prompt 示例：
  "基于以下文档，生成5个不同类型的问答对：
   - 2个事实提取型
   - 1个对比型
   - 1个推理型
   - 1个无法回答型
   文档内容：..."

注意：LLM 生成的评估集需要人工审核！
     否则可能出现"用模型的错误来评估模型"的问题
```

## 8. A/B 测试框架

### 8.1 基本流程

对应 `rag_eval.py` 第5章：

```
场景：对比两种配置的效果差异

  配置 A（baseline）: k=2 检索
  配置 B（candidate）: k=3 检索
       ↓
  同一批评估问题分别跑两个配置
       ↓
  对比评估分数
       ↓
  ┌────────────────────────────────┬────────┬────────┐
  │ 问题                            │ A(k=2) │ B(k=3) │
  ├────────────────────────────────┼────────┼────────┤
  │ 2024年总营收？                  │   5    │   5    │
  │ 净利润和增长？                  │   4    │   5    │
  │ 研发人员和专利？                │   4    │   4    │
  ├────────────────────────────────┼────────┼────────┤
  │ 平均                            │  4.3   │  4.7   │
  └────────────────────────────────┴────────┴────────┘

  结论：配置B比A平均高0.4分 → 建议采用B
```

### 8.2 统计显著性

```
仅仅"平均分更高"不一定靠谱，需要统计检验：

  H0 (零假设): 两种配置效果相同
  H1 (备择假设): 配置B更好

  方法：
    - 配对 t 检验（样本正态分布时）
    - Wilcoxon 符号秩检验（非参数方法）
    - Bootstrap 置信区间

  判断标准：
    p-value < 0.05 → 差异显著，可以接受B
    p-value >= 0.05 → 差异可能是随机波动

  实践建议：
    评估集太小（<30条）时，统计检验意义不大
    评估集 50-100 条时，可以做可靠的统计检验
```

### 8.3 多维度对比

```
不只看"总分"，每个维度单独对比：

  配置 A vs B：
    相关性:  4.2 vs 4.5 (+0.3)  ← 检索改善
    忠实度:  4.5 vs 4.3 (-0.2)  ← 轻微退步（更多文档引入噪音？）
    正确性:  4.0 vs 4.2 (+0.2)  ← 小幅改善

  诊断：
    检索数量增加 → 相关文档更多(好) + 噪音也更多(坏)
    总体收益 > 损失 → 可以采用，但注意忠实度监控
```

## 9. 评估工具生态

### 9.1 RAGAS

```
RAGAS (Retrieval Augmented Generation Assessment)

  开源 RAG 评估框架
  指标：faithfulness, answer_relevancy, context_precision, context_recall
  特点：无需 ground truth 也能评估部分指标

  使用示例：
    from ragas import evaluate
    from ragas.metrics import faithfulness, answer_relevancy

    result = evaluate(
        dataset,
        metrics=[faithfulness, answer_relevancy],
    )
```

### 9.2 DeepEval

```
DeepEval

  面向 LLM 应用的测试框架（类似 pytest）
  指标：correctness, faithfulness, relevance, bias, toxicity
  特点：可集成到 CI/CD

  使用示例：
    from deepeval import assert_test
    from deepeval.metrics import AnswerRelevancyMetric

    metric = AnswerRelevancyMetric(threshold=0.7)
    assert_test(test_case, [metric])
```

### 9.3 LangSmith

```
LangSmith (LangChain 官方平台)

  功能：
    - 自动跑评估 + 历史趋势图
    - 回归检测
    - 标注管理
    - A/B 测试

  特点：与 LangChain 生态深度集成
  适用：已使用 LangChain 的团队
```

### 9.4 工具选型对比

## 10. 持续评估与回归检测

### 10.1 CI/CD 集成

```
将评估集成到开发流程：

  开发者修改代码
       ↓
  提交 PR
       ↓
  CI 自动运行评估脚本
       ↓
  评估分数与 baseline 对比
       ↓
  ┌────────────────────────┐
  │ 分数 >= baseline - δ ? │
  │   是 → ✅ PR通过      │
  │   否 → ❌ 阻止合并    │
  └────────────────────────┘

δ = 容忍的退步幅度（如 0.2 分）
```

### 10.2 回归检测

```
对应 rag_eval.py 中的质量门禁概念：

  THRESHOLD = 3.5  # 最低质量线

  if overall_avg >= THRESHOLD:
      print("✅ 通过！可以部署上线")
  else:
      print("❌ 未通过！需要优化后重新评估")

监控维度：
  - 整体均分的趋势（是否在下降？）
  - 各维度分数的变化（哪个维度退步了？）
  - 最低分案例的变化（新增了哪些"失败"案例？）
```

### 10.3 线上监控

```
上线后的持续监控：

  ① 用户反馈信号：
     - 点赞/点踩比例
     - 重新提问率（用户不满意换个问法再问）
     - 会话放弃率

  ② 自动评估抽检：
     - 每天抽样 N 条线上问答
     - 自动跑 LLM-as-Judge 打分
     - 分数低于阈值则告警

  ③ 边缘情况收集：
     - 收集低分/投诉案例
     - 加入评估集（持续扩充）
```

## 11. 评估驱动开发（EDD）

### 11.1 核心理念

```
EDD (Evaluation-Driven Development)

类比：
  TDD (Test-Driven Development): 先写测试，再写代码
  EDD: 先定义评估标准，再开发 LLM 应用

流程：
  ┌────────────────────────────────────────────┐
  │ 1. 定义评估集 + 指标 + 阈值               │
  │ 2. 跑 baseline（最简实现）                 │
  │ 3. 迭代优化（改Prompt/检索/模型）          │
  │ 4. 每次优化后跑评估                        │
  │ 5. 分数达标 → 上线                         │
  │ 6. 持续监控 → 发现退步 → 回到步骤3        │
  └────────────────────────────────────────────┘
```

### 11.2 评估先行的好处

```
① 明确目标：知道"好"是什么样的
② 量化进展：每次优化都能看到进步（或退步）
③ 防止过拟合：避免对少数案例过度调优
④ 团队对齐：评估标准让所有人有共同的质量标准
⑤ 快速实验：几分钟跑完评估，比人工测试快100倍
```

## 12. 多维度评估体系设计

### 12.1 评估维度矩阵

```
为你的 LLM 应用设计评估体系：

  ┌────────────────────────────────────────────────────────────┐
  │ 维度         │ 适用场景     │ 评估方法       │ 权重建议    │
  ├────────────────────────────────────────────────────────────┤
  │ 正确性       │ 所有场景     │ LLM-Judge      │ 30-40%     │
  │ 忠实度       │ RAG场景      │ LLM-Judge      │ 20-30%     │
  │ 相关性       │ RAG场景      │ LLM-Judge      │ 15-20%     │
  │ 完整性       │ 问答/报告    │ LLM-Judge      │ 10-15%     │
  │ 安全性       │ 面向用户     │ 规则+LLM       │ 10-15%     │
  │ 延迟         │ 实时交互     │ 程序化度量     │ 5-10%      │
  │ 成本         │ 大规模部署   │ 程序化度量     │ 5-10%      │
  └────────────────────────────────────────────────────────────┘
```

### 12.2 综合评分公式

```
加权综合分 = Σ (维度分数 × 维度权重)

示例配置（RAG问答系统）：
  综合分 = 0.35×正确性 + 0.25×忠实度 + 0.20×相关性
          + 0.10×完整性 + 0.10×安全性

门禁规则：
  - 综合分 >= 3.5/5 → 允许上线
  - 安全性 < 3.0 → 一票否决（即使综合分达标也不能上线）
  - 任何维度 < 2.0 → 需要人工审核
```

### 12.3 分级评估策略

```
不同阶段使用不同粒度的评估：

  开发阶段（快速迭代）：
    - 10条核心测试用例
    - 只评1-2个关键维度
    - 秒级反馈

  预发布阶段（全面验证）：
    - 50-100条完整评估集
    - 全维度评估
    - 统计显著性检验

  线上阶段（持续监控）：
    - 每日自动抽检
    - 用户反馈信号
    - 回归告警
```
