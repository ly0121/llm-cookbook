## 1. LLM 记忆问题的本质

### 1.1 无状态 vs 有状态

```
LLM 的本质：一个无状态的函数

  f(输入文本) → 输出文本

每次调用都是独立的，模型不会"记住"上一次对话。

  第1次调用: "我叫张三" → "你好张三！"
  第2次调用: "我叫什么？" → "我不知道你叫什么。"  ← 完全不记得！

这就像每次见面对方都失忆了一样。
```

### 1.2 上下文窗口的本质

```
LLM 的"记忆"完全靠上下文窗口（Context Window）：

  ┌─────────────────────────────────────────────────────────────┐
  │                    上下文窗口 (128K tokens)                   │
  │                                                             │
  │  [系统提示] + [历史对话] + [当前问题] + [模型回答]           │
  │                                                             │
  │  所有"记忆"都必须塞进这个窗口！                             │
  └─────────────────────────────────────────────────────────────┘

问题：
  ① Token 爆炸：100轮对话 ≈ 50000 token → 超出窗口 → 报错
  ② 费用激增：每次调用都发送全部历史 → 按 token 计费
  ③ 注意力稀释：历史太长，模型注意力被分散，关键信息被淹没
  ④ 跨会话失忆：新会话 = 空白上下文 → 昨天的对话全部丢失
```

### 1.3 记忆系统的目标

```
记忆系统 = 在有限的上下文窗口中，放入最有价值的历史信息

核心矛盾：信息量无限 vs 窗口有限

解决思路：
  不是记住所有内容，而是记住"对当前对话最有用"的内容
  → 这就是各种记忆策略的出发点
```

## 2. 记忆系统分类学

### 2.1 按时间维度分类

```
┌────────────────────────────────────────────────────────────────┐
│   类型          │ 时间范围      │ 容量   │ 检索方式            │
├────────────────────────────────────────────────────────────────┤
│   即时记忆      │ 当前轮        │ 极小   │ 直接在 prompt 中    │
│   短期记忆      │ 当前会话      │ 中     │ 窗口/摘要           │
│   长期记忆      │ 跨会话        │ 无限   │ 向量检索/图谱查询   │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 按实现方式分类

```
┌────────────────────┬─────────────────────────────────────────┐
│  策略              │  核心思想                                │
├────────────────────┼─────────────────────────────────────────┤
│  窗口记忆          │  只保留最近 K 轮，超出即丢弃            │
│  摘要记忆          │  用 LLM 压缩旧对话为摘要                │
│  向量记忆          │  向量化存储，按语义相关性检索            │
│  实体记忆          │  提取实体-属性-关系，结构化存储          │
│  知识图谱记忆      │  构建图结构，支持推理和关联查询          │
│  组合记忆          │  多种策略分层组合                        │
└────────────────────┴─────────────────────────────────────────┘
```

### 2.3 人类记忆 vs AI 记忆类比

```
人类：
  感觉记忆 (<1秒) → 短期记忆 (几分钟) → 长期记忆 (永久)
                       ↕ 工作记忆 (加工处理)

AI 对应：
  当前输入 → 窗口记忆 (最近K轮) → 向量/图谱记忆 (全部历史)
               摘要记忆 (压缩版工作记忆)

人类"想起来" = 当前话题触发了长期记忆中的相关片段
AI  "想起来" = 当前问题向量搜索到了历史对话中的相关片段
```

## 3. 窗口记忆（Window Memory）

### 3.1 原理

```
最简单的"防爆"策略：只保留最近 K 轮对话

  K=3 时的对话窗口：
  ┌──────────────────────────────────────────┐
  │  第1轮: "我叫张三"          ← 被丢弃    │  ×
  │  第2轮: "我是开发者"        ← 被丢弃    │  ×
  ├──────────────────────────────────────────┤
  │  第3轮: "我在北京"          ← 在窗口内  │  ✓
  │  第4轮: "我喜欢篮球"        ← 在窗口内  │  ✓
  │  第5轮: "我叫什么？"        ← 当前问题  │  ✓
  └──────────────────────────────────────────┘

  结果：模型无法回答"我叫什么"，因为第1轮已滑出窗口
```

### 3.2 实现

对应 `memory_strategies.py` 中的 `WindowMemory` 类：

```python
class WindowMemory:
    def __init__(self, k: int = 3):
        self.k = k
        self.messages = []

    def get_messages(self) -> list:
        return self.messages[-(self.k * 2):]  # K轮 = 2K条消息
```

### 3.3 优缺点

```
优点：
  ✓ 实现极简（10行代码）
  ✓ Token 消耗固定可控
  ✓ 无额外 LLM 调用成本

缺点：
  ✗ 超出窗口的信息永久丢失
  ✗ 无法处理"很久以前提到的关键信息"
  ✗ K 值选择是个艺术：太小丢信息，太大费 token
```

## 4. 摘要记忆（Summary Memory）

### 4.1 原理

```
不丢弃旧对话，而是让 LLM 压缩为摘要：

  原始对话（500 tokens）:
    用户: 我叫李明，今年32岁，是算法工程师
    AI: 你好李明！
    用户: 我擅长 PyTorch，在研究大模型微调
    AI: 大模型微调是热门方向...
    用户: 目标是今年发顶会论文
    AI: 祝你顺利！

  压缩后的摘要（50 tokens）:
    "用户李明，32岁算法工程师，擅长PyTorch，研究大模型微调，目标今年发顶会论文。"

  压缩比: 10:1！关键信息保留，节省 90% token
```

### 4.2 工作流程

```
  新对话加入
      ↓
  窗口内消息数 > 2K ？
      │
      ├─ 否 → 正常存储
      │
      └─ 是 → 取出最旧的对话
              ↓
         [已有摘要] + [旧对话] → LLM 生成新摘要
              ↓
         用新摘要替换旧摘要
```

### 4.3 Prompt 组装

```
对应 memory_strategies.py 中 SummaryMemory 的使用方式：

  [系统提示]
  [历史摘要]: "用户李明，32岁，算法工程师..."    ← 压缩的历史
  [最近2轮原始对话]                              ← 保持上下文连贯
  [当前问题]
```

### 4.4 优缺点

```
优点：
  ✓ 不丢失关键事实（名字、数字、偏好）
  ✓ Token 消耗可控（摘要长度固定）
  ✓ 信息密度高

缺点：
  ✗ 每次压缩需要额外 LLM 调用（增加延迟和成本）
  ✗ 摘要质量取决于 LLM 能力（可能遗漏重要信息）
  ✗ 细节会丢失（原始措辞、情感细微差别）
```

## 5. 向量记忆（Vector Memory）

### 5.1 原理

```
把每轮对话向量化存入向量数据库，按语义相关性检索：

  存储阶段：
    对话1: "我喜欢吃四川火锅"   → 向量化 → [0.12, -0.34, ...]
    对话2: "我家的猫叫小橘"     → 向量化 → [0.56, 0.23, ...]
    对话3: "我在学 LangChain"   → 向量化 → [-0.11, 0.78, ...]

  检索阶段：
    当前问题: "今晚吃什么好？"  → 向量化 → [0.15, -0.29, ...]
                                       ↓ 计算余弦相似度
    最相关: 对话1 "我喜欢吃四川火锅"  (相似度: 0.87)
    → 把这条记忆放入 prompt → AI 推荐火锅！
```

### 5.2 实现

对应 `memory_strategies.py` 中的 `VectorMemory` 类：

```python
class VectorMemory:
    def add_interaction(self, user_msg, ai_msg):
        content = f"用户问：{user_msg}\nAI答：{ai_msg}"
        doc = Document(page_content=content)
        self.vectorstore = FAISS.from_documents(self.documents, self.embeddings)

    def recall(self, query, k=2):
        return self.vectorstore.similarity_search(query, k=k)
```

### 5.3 优缺点

```
优点：
  ✓ 容量无限（向量库可以存百万条记忆）
  ✓ 按相关性检索（不是按时间顺序，而是按"有用程度"）
  ✓ 天然支持跨会话（向量库持久化即可）
  ✓ 检索速度快（FAISS 毫秒级）

缺点：
  ✗ 需要 Embedding 模型（增加依赖）
  ✗ 语义匹配不精确（"我的猫"和"动物"可能匹配不到）
  ✗ 缺乏时间感知（不知道记忆是昨天还是去年的）
  ✗ 无法表达结构化关系
```

## 6. 实体记忆（Entity Memory）

### 6.1 原理

```
从对话中提取实体及其属性，维护一张"用户画像表"：

  对话过程中提取：
  ┌─────────┬────────────────────────────────────┐
  │ 实体     │ 属性                                │
  ├─────────┼────────────────────────────────────┤
  │ 张三     │ 年龄:28, 职业:Python开发者, 城市:北京 │
  │ 小橘     │ 类型:猫, 品种:橘猫, 主人:张三        │
  │ 公司     │ 名称:XX科技, 方向:AI                 │
  └─────────┴────────────────────────────────────┘

提取 Prompt 示例：
  "从以下对话中提取实体和属性：
   用户说'我叫张三，28岁，在北京做Python开发'
   输出JSON: {实体: '张三', 属性: {年龄: 28, 职业: 'Python开发者', 城市: '北京'}}"
```

### 6.2 与其他记忆的区别

```
窗口/摘要记忆: 记录"发生了什么"（事件级）
实体记忆:      记录"有什么"（知识级）

事件: "用户说他28岁"         → 摘要记忆
知识: "用户.年龄 = 28"       → 实体记忆

实体记忆更适合：
  - 用户画像（偏好、属性）
  - 长期事实（生日、家庭关系）
  - 需要精确召回的信息
```

## 7. 知识图谱记忆

### 7.1 原理

```
将实体之间的关系构建为图结构：

  张三 ──(是)──→ Python开发者
   │                  │
   │(养了)           (使用)
   ↓                  ↓
  小橘              PyTorch
   │                  │
   │(品种)           (属于)
   ↓                  ↓
  橘猫             深度学习框架

优势：支持多跳推理
  问: "张三用什么框架？"
  路径: 张三 → Python开发者 → 使用 → PyTorch
  答: PyTorch
```

### 7.2 实现方式

```
存储后端：
  - Neo4j（专业图数据库）
  - NetworkX（Python 内存图）
  - 自定义三元组存储

三元组格式：(主体, 关系, 客体)
  (张三, 职业, Python开发者)
  (张三, 养了, 小橘)
  (小橘, 品种, 橘猫)
```

## 8. 多层记忆架构

### 8.1 分层设计

```
┌─────────────────────────────────────────────────────────────┐
│                    Prompt 组装顺序                            │
│                                                             │
│  ① System Prompt（角色设定）                 ~200 tokens    │
│  ② 长期记忆（向量检索的 top-K 相关历史）     ~500 tokens    │
│  ③ 实体记忆（相关实体的属性）               ~200 tokens    │
│  ④ 会话摘要（当前会话的压缩版）             ~200 tokens    │
│  ⑤ 最近 K 轮原始对话（窗口内）             ~800 tokens    │
│  ⑥ 当前用户问题                            ~100 tokens    │
│                                                             │
│  效果：短期保持连贯 + 长期提供个性化 + 实体提供精确事实     │
└─────────────────────────────────────────────────────────────┘
```

### 8.2 各层的职责

```
短期记忆（窗口）：
  - 保持对话连贯性
  - 支持代词消解（"它"指的是什么？）
  - 维持对话主题

工作记忆（摘要）：
  - 压缩当前会话的关键信息
  - 保留决策上下文
  - 节省 token 的同时不丢失要点

长期记忆（向量/图谱）：
  - 跨会话的用户偏好和事实
  - 按相关性激活
  - 支持个性化回答
```

## 9. Token 预算管理

### 9.1 预算分配策略

```
以 4K token 上下文窗口为例：

  总预算: 4096 tokens
  ├─ 系统提示:    200 tokens (固定)
  ├─ 长期记忆:    500 tokens (2-3条相关记忆)
  ├─ 摘要:        200 tokens (压缩历史)
  ├─ 窗口对话:    800 tokens (最近2-3轮)
  ├─ 当前问题:    300 tokens (用户输入)
  └─ 预留生成:   2096 tokens (给模型回答用)
      ─────────────
      总计:      4096 tokens

原则：输入 token 不超过窗口的 50%，留一半给生成
```

### 9.2 动态预算调整

```
简单规则：
  if 用户问题很长:   减少历史轮数
  if 需要长回答:     减少记忆注入量
  if 记忆很重要:     增加记忆配额，限制回答长度

高级策略：
  1. 计算当前各部分实际 token 数
  2. 如果总量 > 预算，按优先级裁剪：
     先减长期记忆条数 → 再减窗口轮数 → 最后压缩摘要
```

### 10.2 多用户隔离

```
每个用户拥有独立的记忆空间：

  user_id → {

  vectorstore.add(documents, namespace=f"user_{user_id}")
  vectorstore.query(query, namespace=f"user_{user_id}")
```

## 11. 记忆检索策略

### 11.1 三种检索信号

```
┌──────────────────────────────────────────────────────────────┐
│ 信号          │ 含义                 │ 计算方式              │
├──────────────────────────────────────────────────────────────┤
│ 相关性        │ 与当前问题语义多相似 │ cosine(query, memory) │
│ 时间衰减      │ 越新的记忆权重越高   │ decay^(now - t)       │
│ 重要性        │ 记忆本身的重要程度   │ LLM 评分 / 规则判定   │
└──────────────────────────────────────────────────────────────┘
```

### 11.2 综合评分公式

```
score(memory) = α × relevance + β × recency + γ × importance

其中：
  relevance  = cosine_similarity(query_embedding, memory_embedding)
  recency    = decay_factor ^ hours_since_creation
  importance = LLM_rating(memory_content)  # 1-10分

典型参数：
  α = 0.5 (相关性最重要)
  β = 0.3 (时间有一定影响)
  γ = 0.2 (重要性辅助)
  decay_factor = 0.99

例：
  记忆A: 相关性0.9, 1小时前, 重要性8分
  score = 0.5×0.9 + 0.3×0.99^1 + 0.2×0.8 = 0.45 + 0.297 + 0.16 = 0.907

  记忆B: 相关性0.7, 100小时前, 重要性9分
  score = 0.5×0.7 + 0.3×0.99^100 + 0.2×0.9 = 0.35 + 0.109 + 0.18 = 0.639

  → 选择记忆A
```

## 12. 记忆压缩与遗忘机制

### 12.1 压缩策略

```
渐进式压缩（模拟人类遗忘曲线）：

  原始对话 (详细)
      ↓ 超出窗口后
  段落摘要 (中等详细度)
      ↓ 时间进一步推移
  关键事实 (只保留核心)
      ↓ 重要性低 + 长期不被召回
  删除

类比：
  昨天的会议 → 记得每个人说了什么
  上周的会议 → 记得讨论了什么主题和结论
  去年的会议 → 只记得有这个项目
  三年前     → 完全忘记
```

### 12.2 遗忘机制设计

```
主动遗忘的触发条件：
  ① 存储空间超限 → 淘汰最低分记忆
  ② 时间超过阈值 → 降低权重或删除
  ③ 重复/冗余   → 合并相似记忆
  ④ 被纠正      → 标记为过时

保护机制（不应被遗忘的）：
  - 用户明确要求记住的信息
  - 高重要性评分的事实
  - 最近被频繁召回的记忆
```

## 13. MemGPT / 分层记忆系统

### 13.1 MemGPT 核心思想

```
MemGPT (2023) 将操作系统的虚拟内存概念引入 LLM：

  操作系统：                    MemGPT：
  CPU 寄存器 (极快/极小)   →   上下文窗口 (即时可用)
  内存 RAM (快/中等)       →   工作区记忆 (摘要/缓存)
  磁盘 Disk (慢/无限)      →   外部存储 (向量库/数据库)

  操作系统用"换页"机制在层级间移动数据
  MemGPT 用"记忆管理函数"在层级间移动信息
```

### 13.2 MemGPT 的记忆操作

```
LLM 可以调用的记忆管理工具：

  core_memory_append(key, value)    # 往核心记忆添加信息
  core_memory_replace(key, old, new) # 修改核心记忆
  archival_memory_insert(content)    # 存入档案记忆（长期）
  archival_memory_search(query)      # 从档案中检索
  recall_memory_search(query)        # 从对话历史中检索

核心创新：让 LLM 自己决定什么时候存/取/更新记忆
而不是由外部规则控制
```

### 13.3 与传统方案的对比

```
┌──────────────────┬────────────────────┬────────────────────┐
│                  │  传统记忆管理       │  MemGPT            │
├──────────────────┼────────────────────┼────────────────────┤
│ 存储决策         │ 规则驱动           │ LLM 自主决策       │
│ 检索决策         │ 相似度阈值         │ LLM 判断何时需要   │
│ 更新策略         │ 覆盖/追加          │ LLM 语义更新       │
│ 灵活性           │ 中                 │ 高                 │
│ 成本             │ 低                 │ 高（更多LLM调用）  │
│ 可预测性         │ 高                 │ 低                 │
└──────────────────┴────────────────────┴────────────────────┘
```

## 14. 生产环境记忆方案设计

### 14.1 方案选型指南

```
┌──────────────────────────────────────────────────────────────┐
│  场景                    │  推荐方案                          │
├──────────────────────────────────────────────────────────────┤
│  简单客服 Bot           │  窗口记忆 (K=5) 即可               │
│  长会话助手             │  摘要记忆 + 窗口                    │
│  个性化助手             │  向量记忆 + 实体记忆                │
│  复杂多会话智能体       │  多层架构 (窗口+摘要+向量+实体)     │
│  无限上下文系统         │  MemGPT 风格分层系统                │
└──────────────────────────────────────────────────────────────┘
```

### 14.2 生产架构示例

```
┌─────────────────────────────────────────────────────────────┐
│                    用户请求                                   │
│                      ↓                                       │
│  ┌─────────────────────────────────────────────────────┐    │
│  │              记忆管理层 (Memory Manager)              │    │
│  │                                                     │    │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────────────┐  │    │
│  │  │ 窗口缓存 │  │ 摘要引擎 │  │ 向量检索 + 实体  │  │    │
│  │  │ (Redis)  │  │ (LLM)    │  │ (Milvus+PG)     │  │    │
│  │  └──────────┘  └──────────┘  └──────────────────┘  │    │
│  └──────────────────────────┬──────────────────────────┘    │
│                              ↓                               │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              Prompt 组装器                             │   │
│  │  [系统提示 + 长期记忆 + 摘要 + 窗口 + 问题]          │   │
│  └──────────────────────────────────────────────────────┘   │
│                              ↓                               │
│                          LLM 调用                            │
│                              ↓                               │
│                    记忆更新（存入新对话）                     │
└─────────────────────────────────────────────────────────────┘
```

### 14.3 性能优化要点

```
1. 向量检索异步化：不阻塞主对话流程
2. 摘要批量压缩：积累多轮后一次压缩，减少 LLM 调用
3. 记忆预热：用户登录时预加载常用记忆
4. 缓存层：热门记忆缓存到 Redis，避免重复向量检索
5. 异步持久化：对话结束后异步写入持久存储
```
